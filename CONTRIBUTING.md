# Contributing — SDD Framework

Thank you for contributing. This repo is a **collection of prompts** (commands, agents, templates) — there is no
application code here, so the "test" is consistency, portability and alignment with the SDD philosophy.

## General principles

- **Portability** — nothing may assume a specific stack or project paths. The project's realities
  are described by `ai/docs/` (generated by `/regent:init`), and commands/agents read them as the source of truth.
- **Token economy** — agents read target files via Read (they do not scan `src/`);
  tests in the TDD loop run narrowly (module/pattern), the full `make check` only at gates.
- **Subagent contract** — a subagent does not talk to the user mid-work: approval
  gates are run by the main session, the agent returns artifacts for approval in its report
  (details in `context/subagent.md`).
- **Conciseness** — commands and agents are meant to be short and concrete; no long-winded descriptions.
- **Language** — the "Language" rule in `context/role.md` (artifacts in English).

## Adding a new skill (`skills/<name>/SKILL.md`)

Structure consistent with the existing skills (directory name without a suffix, invoked as `/regent:<name>`):

0. YAML frontmatter: `description` (for the command list), `disable-model-invocation: true` (the skill
   is run by the user; the only exception is pure reading — `MODEL_INVOCABLE` in the lint), `argument-hint` (when there are arguments),
   `allowed-tools` (for read-only commands, e.g. `/regent:explore`, `/regent:status`).
1. Heading `# /regent:<name> — <goal>` + a one-sentence goal.
2. A usage block with arguments and examples.
3. Steps (numbered) with a clear **user approval** point before writing/changes.
4. An "IMPORTANT Rules" section — **phrased positively** (`✅ ALWAYS`): it describes the behavior
   that should happen, not the one that should not. Leave a prohibition (`❌`) only where it
   is a hard guardrail that cannot be expressed positively (e.g. "read-only: no Edit/Write"),
   and then pair it with its goal. The reason is in the "How to write prompts" section.
5. If the skill delegates work — name which **agent** it runs, by the full name `regent:<agent>`.

After adding it, add the skill to the table in `README.md` and `context/sdd-map.md`.

## How to write prompts (commands and agents)

A prompt is read by a model, not a human — and a model reacts to wording differently than intuition
suggests.

**Lead with the positive, not the prohibition.** A prohibition brings the forbidden behavior into the context and makes it
*more* available, not less ("don't think of an elephant"). Negation is a weak modifier —
a strongly activated concept overrides it, so a prohibition half-reads like an instruction.
Write what should happen:

```
❌ "Don't give PASS without a test for the AC"   →  ✅ "PASS requires a test for every AC"
❌ "Don't write verbose reports"                 →  ✅ "Report: verdict + file:line, no code quotes"
❌ "DO NOT scan src/"                            →  ✅ "Read via Read the files named in design.md"
```

When a rule already exists in a positive version, **the twin prohibition is a duplicate** — remove it
instead of keeping both forms. A guardrail that cannot be expressed positively (permissions, tool
boundaries) stays as `❌`, but with its goal stated.

**Use concepts, not descriptions.** A name that lives in the model's pretraining activates a whole class of
patterns; a description of the same thing does not. `Feature Envy` works, "a function reaches too much into other
objects' data" works worse. Repeat the concept as a term, do not expand it into a sentence every time.

**Skip what the model does anyway.** An instruction the model follows by default ("first
reproduce the bug", "check the logs", "write readable code") pays the context cost and adds nothing.
When a whole sentence changes nothing — delete the sentence, do not shorten it.

**The completion criterion must be checkable.** "Understanding has been reached" invites premature
completion; "every AC has a test" and "verification.md written (verdict + date + commit HEAD)"
resolve to a binary answer. When the criterion is fuzzy — sharpen it first.

**Single source.** Describe a rule in one place and refer to it; a description repeated in a second
file drifts apart at the first change. This applies to this principle too: do not repeat it
in commands.

## Adding/changing an agent (`agents/<name>.md`)

Front-matter (YAML) — **required fields**:

```yaml
---
name: <name>
description: >
  <description in English — when to use the agent>
model: opus | sonnet | haiku | inherit
tools: Read, Grep, Glob, Bash          # match to the role; evaluating roles WITHOUT Edit/Write
---
```

- `model` **must** be a real YAML field — never `<!-- model: ... -->` (otherwise it will not work).
- Claude Code recognizes only `name`, `description`, `tools`, `model` — other keys
  (e.g. `language`) are ignored; write language rules in the prompt BODY.
- Model choice: **opus** (high cost of error / deep reasoning — design, security, review),
  **sonnet** (implementation, writing, log instrumentation), **haiku** (very simple, repetitive tasks).
- `tools` choice: evaluating (review, audit) and designing roles — read-only (`Read, Grep, Glob, Bash`);
  implementing roles — with `Edit, Write`.
- Content: Role → "Before you start" (what to read) → Responsibilities/Checklists → Rules →
  **Final report format** (a subagent communicates only through its report).
- **Verdict vocabulary of a verifying agent: `PASS / WARN / BLOCK`** — one for all.
  The FAIL criterion in `/regent:verify` relies on these three words; a dialect of its own
  (`OK/RISKS`, `GAPS`, `APPROVED`) lets a blocking verdict pass as PASS.
  Describe the meaning of the thresholds under the heading — see `dba.md`, `qa-engineer.md`.

## Adding a template

- Change artifact → `templates/<name>-template.md`.
- An `ai/docs/` file → `templates/docs/<name>.md` (a skeleton with `[...]` placeholders, not the realities
  of a specific project). Hook it up in `/regent:init` (the list of generated files).

## Local validation

Run the lint before every commit — in a repo of prompts, it is the test:

```bash
make check      # lint (RESULT: OK) + claude plugin validate . — the gate before every MR
```

It checks the frontmatter of agents and skills, the existence of every referenced skill/agent/template/script,
the `regent:` prefix on agents, the consistency of the tables in `context/sdd-map.md` and `README.md` with `skills/`
and `agents/`, retired names (including the former `-sdd`) and
**regressions** — patterns of fixed prompt bugs (`forbid`/`require` in section 7 of the script).
You fix a prompt bug → add a regression rule in the same commit. The lint also runs
the script tests (`scripts/tests/*.test.sh`) — you change `sdd-check.sh` → add a test case.

**Scripts in `scripts/`** target bash 3.2 (the default on macOS) and POSIX awk: no associative
arrays in bash, no gawk extensions, regular expressions passed to awk via `ENVIRON`
(not `-v`, which interprets escape sequences). A script called by a command is read-only.

## Releases

`master` is the release branch — users install from it, and Claude Code updates the plugin only when
`version` changes. Every merge is therefore a release:

1. In every MR: add the `## [x.y.z] - <date>` entry to `CHANGELOG.md` and run `make bump VERSION=x.y.z`
   (SemVer rules at the top of the changelog). `make check` fails while the version is already tagged.
2. After the merge, on an up-to-date `master`: `make release` (`REMOTE=<remote>` when GitHub is not
   `origin`) — tags `v<version>` and pushes the tag.
3. Rollback: a revert MR with a new version (`v<previous>` stays the reference of the last good code).

## Commits

`<type>: (<KEY>) <description>` — **one line, max 100 characters, no body**. Types: `feat`, `fix`,
`hotfix`, `refactor`, `test`, `chore`, `docs`, `perf`. No ticket → no `(KEY)`.
Atomic commits (1 commit = 1 logical change), never `git add .`.
