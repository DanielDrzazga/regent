# ai/docs, logging and observability

`ai/docs/` is the **single source of truth** about the project for the AI. It is generated by `/regent:init` from the templates
in `templates/docs/`, and commands and agents read it via Read.

## Structure of `ai/docs/`

```
ai/docs/
├── stack/
│   └── technology.md            # runtime, framework, DB, MQ, tests, ports
├── patterns/
│   ├── architecture.md          # type, layers, dependency direction, modules
│   ├── di-patterns.md           # (optional) dependency injection
│   ├── testing-patterns.md      # (optional) pyramid, mocks-first, helpers
│   ├── exception-patterns.md    # (optional) exception hierarchy, handler
│   ├── logging-patterns.md      # (optional) logger: path, API, levels
│   └── frontend-patterns.md     # (optional) UI stack: framework, components, state, API client
├── conventions/
│   ├── naming.md                # files, classes, DB, API, log action
│   ├── code-style.md            # linter/formatter, quality rules
│   └── git-workflow.md          # branching, commits (1 line, max 100 characters)
├── domain/
│   └── glossary.md              # (optional) domain glossary: terms, relations, ambiguities
├── adr/                         # (optional, not from /regent:init) ADRs — created by architect
└── observability/               # (hand-written, NOT from /regent:init) dashboards/alerts
```

Required: `technology`, `architecture`, `naming`, `code-style`, `git-workflow`.
Optional (generated if detected): `di/testing/exception/logging/frontend-patterns`.
`frontend-patterns.md` is the source of truth for the `regent:frontend-dev` agent — without it, it does not
implement UI (analogous to `logging-patterns.md` ↔ `/regent:logging`).

## Maintenance rules

- Make changes to `ai/docs/` through `/regent:revise` — other agents read from them, so a "silent"
  change throws their context out of sync.
- The templates in `templates/docs/` are **skeletons** with `[...]` placeholders; the realities of a specific
  project are filled in by `/regent:init` per project.

## Logging (`logging-patterns.md`)

The source of truth for `/regent:logging` and the `regent:logging-engineer` agent. It describes the **existing** logger:
the import path, the API (`business()` / `technical()` or native), the levels (`debug`→`fatal`),
the `action` convention (`NOUN_VERB`, UPPERCASE, EN), the security rules.

Hard instrumentation rules:

- Only entity IDs in `context` — **zero PII/secrets**.
- One log per operation — not in a loop / hot path.
- Do not log in `domain/` — only application/infrastructure/interface.
- Do not build/extend the logger — this is instrumentation, not a `LoggerModule`.

No file → `/regent:logging` asks the user (it does not guess the logger path).

## Observability (optional)

If the project maintains `ai/docs/observability/` (e.g. Kibana dashboards/alerts), `action` values
are often hardcoded in panel filters — so **a change of `action` silently breaks the dashboard**.

The framework enforces reflection (not building dashboards):

- `/regent:logging` Step 4.5 and `regent:logging-engineer` — flag adding/changing/removing an `action`.
- `/regent:verify` Stage 7 — the conditional checklist from `observability/maintenance.md`.
- `logging-patterns.md` — a section linking to observability.

Typical content of `observability/`: `maintenance.md` (a "change in code → what to do" map),
`kibana-dashboard.md`, `dashboard-panels.md`, `alerts/` (rule definitions). You create them manually —
`/regent:init` does not generate them (they are too environment-specific: index patterns, webhooks).
